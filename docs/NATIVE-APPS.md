# Native application launcher

The `0.0.1-pilot.15` candidate connects the native launcher to an explicitly enrolled ordinary user on Raspberry Pi OS Trixie 64-bit Desktop. It includes Writer, Calculator, Documents/Downloads, Paint, Files, Trash and the game catalog. Actual Linux VM checks have verified Applications launching Paint, OpenTTD, Calculator and Writer. Physical Pi installation remains pending. The [Sunday 11 October install guide](../os/raspberry-pi/SUNDAY.md) describes the Pi 5, 8 GB target and checks.

## User experience

Paint, Writer, Calculator and Files have normal desktop, Applications and Start entries. My Stuff links to native Documents, Pictures and Downloads; it continues to own source Projects and project Trash separately. Native games remain in Play and Applications. The optional proprietary Putt-Putt demo has no prominent desktop or Start shortcut, is not distributed, and reports unavailable on the Pi. OpenTTD uses its separately installed open asset packages. Each catalog entry reports missing packages or unprepared folders honestly.

Native apps open ordinary Linux windows. Launching them does not create an iframe or a saved browser-window descriptor. Existing project applications, game scores and workspace recovery keep their current contracts.

The macOS browser preview shows the same tools and folders but cannot launch Linux software. An unavailable bridge or missing package produces a clear message rather than a successful-launch claim. The Pi launcher uses a maximized application window and retains the normal Pi panel for sound, input, power and switching native windows. Native registration also adds a kidOS entry to the Pi application menu; optional XDG autostart preserves normal login and desktop configuration. The disposable VM alone has its existing F8/F9/F10 shortcuts. A fully integrated browser/native taskbar remains later work.

## Authority and transport

The desktop communicates with an explicitly installed Chromium extension, which uses Chromium Native Messaging to contact an ordinary-user host. The web-facing operations are a fixed application catalog and launch by a known app ID. Requests cannot supply executable names, command arguments, filesystem paths, environment variables or install operations.

The extension must accept only the exact desktop origin and top frame, independently validate the browser sender, and reject runner frames and unrelated sites. The native host must independently validate bounded requests and the extension identity before using its fixed catalog. This is a supervised native-app integration, not containment against another process running as the same Unix user.

The platform service has no native launch endpoint and receives no desktop-session credentials, home-directory access or additional privileges. Its existing `ProtectHome`, `PrivateDevices`, `ProtectSystem` and service identity remain unchanged. No API token crosses into a native program. Native files and saves remain separate from the service's private project and Library data; see [the everyday-computer proposal](EVERYDAY-COMPUTER.md).

Pi setup validates physical hardware, Trixie/ARM64, the installed service/runtime, fixed application files and the selected existing desktop identity before registration. The desktop username must not be `kidos`, which is reserved for the locked service. Ordinary-user setup creates missing folders and private preferences under `~/.local/share/kidos-native`, without overwriting existing work. Backups need both the complete stopped service directory and the ordinary user's files, native saves/preferences, Trash and closed browser profile; see [the Pi backup steps](../os/raspberry-pi/SUNDAY.md#5-preserve-work-before-updates-or-recovery-tests).
